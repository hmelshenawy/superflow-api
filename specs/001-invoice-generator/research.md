# Research: Invoice Generator

**Feature**: Invoice Generator
**Date**: 2026-06-05

## Unknowns Resolved

### PDF Generation Library
- **Decision**: Reuse existing `pdfkit` (already in package.json and used by `src/billing/invoice-pdf.service.ts`)
- **Rationale**: PDFKit is already installed (`pdfkit ^0.18.0`), has `@types/pdfkit`, and the billing module already generates A4 PDFs. Adding a second PDF library would increase bundle size and maintenance. The existing `InvoicePdfService` patterns (A4 portrait, table rendering, currency formatting) can be adapted for workshop invoices.
- **Alternatives considered**: Puppeteer (heavier, requires Chromium), jsPDF (different API, no existing usage)

### Workshop Invoice vs. Subscription Invoice Naming
- **Decision**: New Prisma model named `workshop_invoices` with relation `workshop_invoice_items`
- **Rationale**: The existing `invoices` / `invoice_items` models handle SaaS subscription billing and are queried via `prisma.raw` (unscoped). Workshop customer invoices are tenant-scoped and have different fields (discounts, line-item types, snapshots, job links). Keeping them separate prevents schema confusion and data corruption.
- **Alternatives considered**: Reusing `invoices` with a `type` discriminator — rejected because the existing model is tightly coupled to subscriptions (payments, plans, subscription_id) and is unscoped.

### Workshop Branding Storage
- **Decision**: Extend `workshops` table with new nullable columns for branding fields
- **Rationale**: The `workshops` model already contains `name`, `address`, `phone`, `email`. Adding `logo_url`, `vat_trn`, `footer_notes`, `terms_conditions` columns is the simplest approach and keeps branding co-located with the workshop record. No new entity needed.
- **Alternatives considered**: New `workshop_profiles` table — rejected as unnecessary abstraction for v1; settings JSON blob — rejected because typed columns are clearer and easier to query.

### Invoice Numbering
- **Decision**: Auto-generated by backend in format `{WORKSHOP_CODE}-{BRANCH_CODE}-{YEAR}-{SERIAL}` (e.g., `GAR-DEI-2026-000001`). Serial is sequential per workshop + branch + year and resets annually. A dedicated `workshop_invoice_sequences` table tracks `last_serial_number` per (`workshop_id`, `branch_id`, `year`).
- **Rationale**: Financial references must remain stable even if workshop/branch codes change later, so `workshop_code_snapshot` and `branch_code_snapshot` are stored on the invoice at creation. The `workshop_invoice_sequences` table with Prisma transaction-level locking prevents duplicate numbers under concurrent creation. Users cannot manually edit invoice numbers in v1.
- **Alternatives considered**:
  - UUID — rejected because invoice numbers must be human-readable and sequential for accounting traceability.
  - Manual entry with duplicate check — rejected because it creates user friction and does not guarantee uniqueness under race conditions.
  - Single global sequence — rejected because different branches need independent serials.

### Permission Naming
- **Decision**: `INVOICES_READ`, `INVOICES_CREATE`, `INVOICES_UPDATE`, `INVOICES_CANCEL`, `INVOICES_EXPORT`
- **Rationale**: Follows existing `category:action` pattern. `INVOICES_DELETE` is intentionally excluded — invoices are soft-cancelled, not deleted, per spec EC-010.

### Snapshot Storage
- **Decision**: Snapshot fields stored directly on `workshop_invoices` table as `snapshot_*` columns
- **Rationale**: Flat columns (customer_name, customer_phone, customer_email, vehicle_plate, vehicle_vin, vehicle_model, vehicle_year) are simpler than a JSON blob or a separate snapshot table. They are read-only after issuance and make PDF generation straightforward without extra joins.
- **Alternatives considered**: JSON snapshot blob — rejected because typed columns are queryable and Prisma-friendly; separate `invoice_snapshots` table — rejected as over-engineering for 7 fields.

### VAT Calculation Approach
- **Decision**: Each line item stores `vat_applicable` boolean and `vat_rate` decimal. Backend computes line VAT = (qty * unit_price - discount) * vat_rate when applicable.
- **Rationale**: Per-line VAT applicability is required (some parts may be exempt). The VAT rate is read from workshop settings at invoice creation time. Centralizing calculation in the service ensures explainability and prevents frontend drift.
